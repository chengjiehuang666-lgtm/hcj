# 分级路由实施计划

## 目标与验收

- **目标**：P95 端到端时延 133.8 秒 → **≤ 60 秒**（达成 M1 的时延目标）
- **验收标准（按你的选择）**：成功率 **≥ 90%**（允许从 20/20 降至 18/20）+ **P95 ≤ 60 秒**
- 若两者不可兼得或 P95 仍不达标 → 如实报告，不粉饰

勘察已确认：业务侧**只有一个网关调用点**（`agents/base.py:124`），因此改动面小；但 `PipelineOutcome` 目前**没有逐次调用明细**（`LLMGateway.history` 在 `run()` 结束后即丢弃），做成本归因需补一条记录通道。

## 核心设计

按**调用点**（而非仅按 Agent 角色）路由。原因：Analyst 的两次调用性质完全不同——「生成 SQL」是机械翻译，「归因」是真推理，正是分级路由最该区分的地方。

新增两个档位：
- **reasoning 档** = 现有的 `LLM_PRIMARY_*` / `LLM_FALLBACK_*`（DeepSeek deepseek-flash）
- **fast 档** = 新增 `LLM_FAST_PRIMARY_*` / `LLM_FAST_FALLBACK_*`

路由表用 JSON 环境变量表达，改路由不用改代码：

```
LLM_ROUTING={"planner":"reasoning","analyst_sql":"fast","analyst_conclude":"reasoning"}
```

## 阶段 1：引入路由机制（行为不变）

先把机制建好，**所有调用点仍指向 reasoning 档**，确保零行为变化。

1. **`gateway/base.py`** — `CallRecord` 增加 `route: str | None = None` 与 `duration_ms: int = 0`
2. **`gateway/gateway.py`** — `LLMGateway.complete()` 增加 `route: str | None = None` 参数（自身忽略，仅为与路由器统一签名），写入 CallRecord；新增 `build_router_from_settings()`
3. **新增 `gateway/router.py`** — 路由常量（`ROUTE_PLANNER` / `ROUTE_ANALYST_SQL` / `ROUTE_ANALYST_CONCLUDE` / `ROUTE_DEFAULT`）+ `ModelRouter`（`complete(messages, *, route=None, …)`、`gateway_for(route)`、跨档聚合的 `history`）
4. **`config.py`** — 新增 fast 档 8 个字段、`fast_primary`/`fast_fallback` 属性、`llm_routing: dict[str, str]`（默认全 reasoning）
5. **`agents/base.py`** — `call_json()` 增加 `route` 参数，L124 改为 `complete(messages, route=route, max_tokens=…)`
6. **`agents/planner.py` / `analyst.py`** — 各自传入 route；analyst 的 `_generate_sql` → `analyst_sql`、`_conclude` → `analyst_conclude`
7. **`graph/pipeline.py`** — 改用 `build_router_from_settings`；`PipelineOutcome` 增加 `call_records: list[dict]`
8. **测试** — `FakeGateway.complete` 增加 `route=None` 并记录 `routes_seen`；新增路由分发/降级/明细断言；新增 `tests/test_model_router.py`。现有 `test_gateway.py` 断言不受影响（route 默认 None）

## 阶段 2：测量归因（先量后改）

跑 5 条代表性用例（路由仍全 reasoning），从 `call_records` 读出**每个调用点的 token 与耗时占比**。

目的：确定耗时主体到底是「生成 SQL」还是「归因」，避免凭猜设路由表。这一步直接决定阶段 3 的路由表内容。

## 阶段 3：按数据设置路由表并验收

- `.env`：fast 档主模型 = 本地 `glm-5.3`（你确认是常驻服务），备 = `deepseek-flash`
- `.env.example`：写入本地地址（已确认可长期依赖）+ 各字段用途注释
- 跑完整 20 条，按 **≥90% 成功率 + P95 ≤60 秒** 判定

## 明确的非目标

- **不动任何已冻结的契约**（`AgentResult` / `TokenUsage` / `TaskEvent` 等）。路由是网关内部机制；逐次调用明细只落在 `PipelineOutcome`（内部结构，不是契约）
- 不引入 LiteLLM 或任何新第三方依赖（架构文档允许自研，且现有栈已够）
- 不做语义缓存、不做「按任务标签自动选模」（属后续版本）
- 不改 LangGraph 图结构（仍是固定串行链路，动态 DAG 属 W5）

## 风险与对策

| 风险 | 对策 |
| :--- | :--- |
| 切 fast 后 SQL 质量下降，成功率跌破 90% | 评测会直接暴露；回退该调用点到 reasoning 档只需改 `.env` 一行 |
| 本地端点重启/不可用 | fast 档的备模型是 deepseek-flash，自动降级，不失败，只是时延回退 |
| 耗时主体其实是「归因」而非「生成 SQL」 | 说明路由解决不了，需换更快的推理端点；我会如实报告并给建议 |
