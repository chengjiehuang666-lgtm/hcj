# 1. 产品需求（Product Requirements）

## 1.1 核心场景定义

本项目定位为**企业级多 Agent 智能协作平台**：以一个中央调度 Agent（Orchestrator）统筹多个具备专属技能的专家 Agent，通过任务分解、并行执行、交叉校验与人工介入，将过去需要多人跨岗位协同完成的复杂知识工作，改造为「一次提需求、多 Agent 自动交付、关键节点人工确认」的自动化流水线。

平台采用「通用编排内核 + 可插拔业务 Agent」的设计，不绑定单一业务，首批落地以下 4 个高价值场景：

| 场景 | 触发方式 | 协作链路（Agent 流转） | 最终交付物 | 落地批次 |
| :--- | :--- | :--- | :--- | :--- |
| **数据分析流水线** | 用户用自然语言提出分析诉求 | 规划 Agent → 取数 Agent → 分析 Agent（含图表生成） → 评审 Agent | 带图表与结论的分析报告 + 可回溯 SQL | **① 阶段一（MVP）** |
| **报告/文档自动化** | 输入主题与素材 | 检索 Agent → 规划 Agent → 写作 Agent → 审校 Agent →（人工签发） | 结构化正式文档（Markdown/Word/PDF） | **② 阶段二** |
| **智能客服与工单** | IM / 工单系统接入 | 接待 Agent → 检索 Agent（知识库 RAG）→ 业务办理 Agent →（必要时）人工坐席 | 客户答复 + 自动建工单 + 处理记录 | ③ 延后（需扩员） |
| **代码生成协作** | 提交 Issue / 需求描述 | 规划 Agent → 编码 Agent → 测试 Agent → 评审 Agent →（人工 Merge） | 可运行代码 + 单元测试 + 评审意见 | ③ 延后（需扩员） |

> **范围说明（2026-10-16 确认）：** 项目为**单人全职开发**（见《实施路线图》3.1）。上表 4 个场景不是并行启动的目标，而是**按批次串行落地**：阶段一先打通「数据分析流水线」一条链路，阶段二追加「报告/文档自动化」。③ 两类的落地依赖扩员，本期不做。
>
> **D6 决议（2026-10-19）：** 首批试用用户 = 项目所有者 + 1–2 名内部数据分析/运营同事（W9 安全基线前不对外部客户开放）；第 3 场景优先级 **智能客服与工单 > 代码生成协作**，扩员后启动；本期 W9–W12 不启动第 3 场景。
>
> 原链路中的**「图表 Agent」已并入分析 Agent**（其技能集本就包含图表库），不再单列为独立 Agent，以降低 MVP 阶段的编排复杂度。

**目标用户与角色：**

- **业务人员（运营/市场/管理）**：自然语言提需求，获取分析与文档，不接触技术细节。
- **研发/数据工程师**：提交代码、取数、排障任务，使用平台生成的可追溯中间产物。
- **审核/管理者**：在关键节点（对外发数据、合并代码、签发文档）进行人工审批（Human-in-the-loop）。
- **平台管理员**：配置 Agent、工具权限、模型配额、审计策略与成本看板。

**核心业务价值（可量化指标）：**

- 数据分析任务平均交付时长由 **4 小时缩短至 30 分钟以内**；
- 客服首响时间 < **3 秒**，常见问题自动闭环率 ≥ **70%**；
- 标准化文档生成耗时下降 ≥ **60%**，一次审校通过率 ≥ **80%**；
- 全链路可追溯：每个结论可回溯到来源数据、调用工具、模型版本与责任 Agent。

> **指标口径说明（2026-10-16 补充）：** 上表是**业务价值指标**，衡量组织效率而非系统性能，两者不可混用。
> 以「4 小时 → 30 分钟」为例，它指的是**人工跨岗位协作的全部耗时**（含沟通、排期、取数排队、等待审核），与《实施路线图》M1 的「单任务端到端时延 ≤ 60 秒」不是同一个指标——后者是**系统从收到任务到产出结果的机器耗时**。
> 验收时请分别引用：业务价值指标由业务方在试用期结束后评估，系统性能指标由压测报告（W11）给出。

## 1.2 功能模块清单

### 1.2.1 任务接入与会话模块（阶段一 · 部分落地）
- **多渠道接入网关**：统一接入 Web 控制台、企业 IM（飞书/钉钉/企微）、REST API、工单系统 Webhook；功能描述：将不同渠道消息归一化为标准任务事件。预期价值：业务零改造接入。**（本期只做 REST；W13 增补轻量 Web 控制台；IM / Webhook 渠道延后）**
- **意图理解与任务分诊**：基于大模型对输入做意图分类、参数抽取、紧急度/敏感度分级。预期价值：自动路由到正确流程，敏感任务自动升级管控。
- **多轮会话管理**：维护会话上下文、追问澄清、会话断点续接。预期价值：支持模糊需求的渐进澄清。

### 1.2.2 任务规划与编排模块（阶段一 · 部分落地）
- **任务分解（Plan-and-Solve）**：将复杂目标拆解为带依赖关系的 DAG 子任务图，明确每个子任务的负责 Agent、输入输出契约（Schema）与验收标准。**（~~阶段一为固定串行链路，DAG 暂不动态生成~~ → 已于 W5 升级为动态生成：Planner 产出 DAG 在运行时驱动构图与并行执行；W6 起可产出 reviewer / writer 节点）**
- **动态重规划**：子任务失败或结果不达标时，自动重新分解、更换 Agent 或补充检索步骤。**（阶段二落地）→ 已实现（W7，有界）：节点重试耗尽或 Agent 判定拆解不可行（`needs_replan`）时触发一次重规划（`revision+1`）；评审 fail 不触发返工（W6 的取舍，待评审标准按问题类型校准后再议）；条件分支仍延后**
- **编排可视化**：以流程图实时展示任务 DAG、执行状态、当前节点与耗时。预期价值：过程透明、可人工干预。**（延后，需前端工程）→ W13 已增补轻量控制台：DAG SVG（按依赖分层、状态着色）+ SSE 实时事件 + 节点耗时/Token；拖拽编辑与完整前端仍延后**

### 1.2.3 Agent 调度与协作模块（阶段一 · 部分落地）
- **中央调度（Orchestrator）**：按 DAG 路由分发子任务，解决 Agent 间的资源争用与结论冲突。**（~~阶段一为串行调度；阶段二升级为动态并发调度~~ → 已于 W5 升级为动态并发调度：DAG 驱动运行时构图，同层无依赖节点并行执行）**
- **专家 Agent 池**：检索、编码、分析、测试、评审、写作等可插拔 Agent，支持热加载与版本管理。**（本期只实现 4 个：Planner / Retriever / Analyst / Reviewer）→ 实况（2026-10-16）：Planner / Retriever / Analyst / Reviewer / Writer 五个均已交付；Reviewer 属阶段一「核心价值不可砍」项，由 W6 补齐**
- **协作模式库**：内置串行流水线、并行竞速（Race）、投票（Voting）、多 Agent 辩论（Debate）、反思（Reflection）等模式。**（本期只保留串行 + Reflection 交叉校验；其余延后）→ 已落地（W6）：Reviewer 逐条核对验收标准与证据（Reflection 交叉校验），并以黑板乐观锁把上游条目流转为 validated / rejected；Voting / Debate / Race 仍延后（竞速与条件分支属 W7）**
- **人工介入（HITL）**：在高风险节点暂停并推送审批，支持批准、驳回、改写、转人工。**（阶段二落地后端阻塞点；审批 UI 延后）→ 已实现（W7）：`POST /tasks/{id}/approval` 支持批准 / 驳回（独立终态 `rejected`）/ 改写（人工提供替换产物，写回黑板并标注来源）；暂停状态 `awaiting_approval` 可查询、可跨进程恢复；审批 UI 仍延后**

### 1.2.4 记忆与知识管理模块（阶段一 · 落地）
- **短期工作记忆**：单次任务内的中间结果、变量与步骤状态（Redis + 图状态 Checkpoint）。**（实况：图状态 Checkpoint 已落地于 PostgreSQL；单进程部署下 Redis 未用于工作记忆）**
- **长期共享记忆**：跨会话沉淀的事实、用户偏好、历史结论，基于向量库语义检索（含来源与时效）。**（本期载体为 pgvector，与 PostgreSQL 同实例）→ 已实现（W6）：独立表 `memory_entries`（与知识库分表；512 维向量 + `pg_trgm` 混合检索）；条目带来源 / 时间 / 置信度；沉淀门槛为「任务成功 + Reviewer 未否决」；检索只返回 validated 且未过期条目；历史结论回灌提示词时明确标注「仅供承接回顾、不得作本次数据证据」**
- **企业知识库（RAG）**：接入文档、Wiki、数据库 Schema、FAQ，支持增量索引与权限隔离。**（本期为单租户、无行级权限隔离，权限过滤雏形在阶段二）**
- **黑板（Blackboard）**：所有 Agent 共享的任务工作区，任一 Agent 写入后其他 Agent 可订阅。**（本期为 Agent 间唯一交换介质，契约见 `blackboard_entry.schema.json`）→ 已落地（W6）：条目按冻结契约构造（含 task_id / 版本号 / 写入者 / 状态）；覆盖写入走**条目级乐观锁**（提交读到的 version，不符即拒绝）；订阅=下游节点按依赖获得上游条目与来源明细（`visible_blackboard_keys` 已填充）；变更通知走进程内事件通道（Redis Stream 移至多进程阶段，见《系统架构设计》2.2.3）**

### 1.2.5 工具调用与集成模块（阶段一 · 部分落地）
- **统一工具协议**：基于 MCP（Model Context Protocol）+ Function Calling 接入搜索、数据库、HTTP API、代码执行、文件处理等工具。**（本期只开放 SQL 查询、Python 沙箱、知识库检索三项；MCP 标准化的完整接入延后）**
- **代码执行沙箱**：隔离运行 Python/SQL/脚本，限制网络、文件系统与资源配额。**（本期为进程级隔离：只读 SQL 连接 + 超时/行数上限 + subprocess 资源限制；gVisor 级容器隔离延后）**
- **企业系统连接器**：数据库、Git、Jira、工单、对象存储、邮件等开箱即用连接器。**（延后，依赖具体业务系统落地）**

### 1.2.6 安全与合规模块（阶段三 · 降级落地）
- **统一认证与权限（RBAC + ABAC）**：用户、Agent、工具三级权限，按角色 + 数据属性（密级/部门）双重判定。**（本期降级为 API Key + 简单角色权限，单租户；完整 RBAC+ABAC 延后）→ 已实现（W9）：API Key + admin/operator/viewer 三角色（读取 / 提交 / 审批），启用鉴权但未配置 Key 时拒绝启动；不做用户体系与行级权限**
- **输入过滤与提示注入防护**：对用户输入与外部检索内容做敏感词、越权指令、Prompt Injection 检测与隔离。**（本期为规则层过滤）→ 已实现（W9）：6 类注入规则 + 敏感词 + NFKC/零宽/空格归一化绕过防护；输入中的身份证/手机号/银行卡/密钥就地脱敏；命中注入在 API 返回 400 `INPUT_BLOCKED`，编排层入口再兜底。**外部检索内容的「不可信数据」隔离标注仍未做**（RAG 片段直接进提示词）**
- **输出审计与脱敏**：对外输出经规则 + 模型双层校验，自动脱敏身份证、手机号、密钥、财务数据。**（本期只做规则层脱敏/正则识别，模型层延后）→ 已实现（W9）：身份证 / 手机号 / 银行卡（Luhn 校验防误伤）/ 密钥与令牌正则脱敏，覆盖 API 结果、SSE、CLI 与长期记忆沉淀；422 校验错误不回显原始输入。财务数字与模型层识别仍延后**
- **数据隐私与留存**：数据分级分类、传输/存储加密、可配置留存周期与删除策略，支持私有化部署。**（本期只做私有化单机部署；分级分类与留存策略依赖 D5 待定项）→ W12 已交付单机 docker-compose 部署、冒烟与按 Git 标签回滚（M3 达成）；传输加密、留存策略仍延后**

### 1.2.7 可观测与运营模块（阶段三 · 降级落地）
- **全链路追踪**：每次任务记录 Agent、模型、Prompt、工具调用、Token、耗时与产物，支持 OpenTelemetry 链路。**（本期为结构化日志 + `task_id` 贯穿，OTel 延后）→ 已实现（W10）：JSON 结构化日志，`task_id` 经 ContextVar 贯穿网关/Agent/工具；日志只记长度/哈希/token/耗时，不落原始 prompt/输出**
- **成本与配额管理**：按部门/用户/Agent 统计 Token 与费用，设置预算与限流。**（本期为按任务/Agent 的 Token 成本计量，看板以命令行/简单页面呈现；部门配额延后）→ 已实现（W10）：按调用点/Agent/模型汇总 token 与成本，写入任务结果、评测报告与 `GET /metrics`；成本单位是本地端点积分，不是货币；部门配额与限流仍延后**
- **质量评测与回归**：维护场景评测集，对模型/Prompt/Agent 版本做离线打分与灰度对比。**（本期评测集 + 离线打分保留，灰度对比延后）→ W8 已扩至 50 条（分析 29 / 文档 20 / 跨会话记忆 1），按场景设 ≥90% 门槛，并交付三层压测工具（端点 / 编排 / 全链路）；灰度对比仍延后**
- **监控告警**：对成功率、延迟、异常率、工具失败率设置阈值告警。**（延后，需监控栈）**

### 1.2.8 多模型网关模块（阶段一 · 部分落地）
- **统一模型路由**：一套接口对接多家大模型（GPT/Claude/DeepSeek/Qwen/豆包等），按任务难度与成本选择模型。**（阶段一实现统一调用 + 主备两模型降级）**
- **降级与负载均衡**：供应商故障自动切换，高峰期排队与限流，支持私有化模型兜底。**（阶段一实现故障切换；排队限流延后）**
- **Prompt 与版本管理**：集中管理各 Agent 的系统提示词、模板与版本，支持灰度与回滚。**（阶段二落地：Prompt 集中管理 + 版本化；灰度延后）**

## 1.3 Agent 角色体系

| Agent 角色 | 职责定义 | 技能/工具集 | 落地批次 |
| :--- | :--- | :--- | :--- |
| **调度编排 Agent（Orchestrator）** | 全局任务路由、DAG 调度、冲突仲裁、异常重规划、人工节点触发；不直接产出业务内容 | 规划引擎、状态机、DAG 运行时、HITL 接口、配额熔断 | ① 阶段一（串行）→ 阶段二（动态并发） |
| **需求规划 Agent（Planner）** | 澄清需求、任务拆解、定义子任务输入输出契约与验收标准 | Plan-and-Solve / CoT、Schema 校验、澄清话术库 | ① 阶段一 |
| **知识检索 Agent（Retriever）** | 企业知识库与外部信息检索、多路召回、重排序、来源标注 | 向量检索、关键词检索、Reranker、网页/文档连接器、SQL 元数据查询 | ① 阶段一 |
| **数据分析 Agent（Analyst）** | 取数、清洗、统计建模、归因分析、生成图表与结论 | SQL 执行、Python（pandas/numpy）、图表库、指标口径库 | ① 阶段一（**已并入原「图表 Agent」职责**） |
| **编码 Agent（Coder）** | 按需求生成/修改代码、编写脚本、修复缺陷 | 代码生成、Git、文件读写、语言运行时、依赖管理 | ③ 延后（需扩员） |
| **测试 Agent（QA）** | 生成单元/集成测试、执行用例、回归验证、报告缺陷 | 测试框架、沙箱执行、覆盖率工具、Mock 服务 | ③ 延后（需扩员） |
| **评审 Agent（Reviewer/Critic）** | 对其他 Agent 的产物交叉校验，识别幻觉、逻辑错误、安全与合规问题 | Reflection / 辩论模式、规则引擎、事实核查、静态检查 | ① 阶段一（**核心价值，不可砍**）→ **已于 W6 交付**（分析/文档任务强制必审：逐条核对验收标准与证据，verdict=fail 才否决） |
| **写作 Agent（Writer）** | 生成报告、文档、客服话术，按模板与风格要求成稿 | 模板引擎、文档转换（Markdown/Word/PDF）、风格规范库 | ② 阶段二（文档场景）→ **已于 W6 交付并端到端跑通**（检索→写作→审校） |
| **业务办理 Agent（Operator）** | 在客服场景调用业务系统完成查询、下单、改单、建工单等动作 | 业务 API、工单系统、表单填写、二次确认机制 | ③ 延后（需扩员） |
| **安全审计 Agent（Guardian）** | 独立于业务链路，对输入、工具调用、输出进行安全与合规审计与拦截 | 输入过滤、脱敏、DLP、权限判定、审计日志写入 | 阶段三（**降级为内置安全中间件，暂不单列为独立 Agent**） |

**协作机制约定：**

1. **单一事实源**：所有子任务结果写入共享黑板，Agent 不直接互相传递私有状态，避免状态分叉。
2. **契约先行**：子任务之间以结构化 Schema（JSON Schema / Pydantic）传递数据，校验失败即退回重做。
3. **关键节点必审**：涉及对外发送、资金/数据变更、代码合并、文档签发的节点，强制经评审 Agent + 人工双重确认。
4. **预算与步数约束**：每个任务设置最大执行步数、最大 Token 与最大重试次数，超限自动熔断并转人工。**（已实现，W7：编排层统一计数，节点启动前检查；超限以稳定错误码终止并发事件。单租户无审批队列，「转人工」的落点是任务停在可观测状态）**
