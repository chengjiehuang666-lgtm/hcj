## 3.1 总体策略、节奏与人力

**人力规模：1 人（全职）。无前端、无运维、无测试专职。**

由此推导出三条硬约束，它们决定了后面所有排期与范围：

1. **一切并行皆串行。** 原四线并行的总工期不能除以 4，必须按串行重新估算：阶段之间没有重叠，一个人一次只能推进一条线。
2. **不做平台工程。** 网关、消息总线、服务网格、多租户、集群化，对单人项目是纯负债而非资产，一律延后或砍掉（详见《系统架构设计》「实施范围声明」）。
3. **「每周可演示」不成立，改为「每里程碑可演示」。** 每个阶段预留 20% 缓冲——单人没有任何冗余人力，缓冲是唯一的抗风险手段。

仍然坚持的原则：垂直切片、契约先行（Schema 先冻结）、文档与代码一致、每个稳定功能立即提交。

| 阶段 | 周期 | 核心目标 | 出口标准（Definition of Done） |
| :--- | :--- | :--- | :--- |
| **阶段一 MVP 验证期** | Weeks 1–4 | 单场景单链路真的跑通 | 数据分析场景端到端可演示，20 条评测用例成功率 ≥ 80% |
| **阶段二 协同深化期** | Weeks 5–8 | 动态编排 + 多 Agent 协同 + 人工介入 | 2 个场景可用，成功率 ≥ 90%，熔断与 HITL 可触发 |
| **阶段三 可用化期** | Weeks 9–12 | 安全基线、可观测、可私有化单机部署 | 单机 docker-compose 可部署，冒烟通过，可回滚 |

> ⚠️ **相对原方案的出口标准下调**：原阶段三要求「K8s 高可用 + 多租户 + 灰度发布 + 99.9% 可用性 + 混沌测试」，这是 3–4 名专职工程师一个季度的工作量，单人不可达，**已整体移出本期范围**。若该目标不可让步，本项目需扩员至 3–4 人，或周期拉长至 20 周以上。

## 3.2 阶段一：MVP 验证期（Weeks 1–4）

- **目标**：用最小链路验证「规划 → 取数 → 分析 → 评审」的技术可行性，打通模型网关、LangGraph 编排、工具调用与最小交互入口。
- **范围收敛**：只做「数据分析流水线」1 个场景；只接入 1 个主模型 + 1 个备模型；工具只开放 SQL 查询、Python 沙箱、知识库检索 3 项。

### 周计划

| 周次 | 关键任务 |
| :--- | :--- |
| **W1** | **先冻结接口契约**（`TaskEvent` / `SubtaskDAG` / `BlackboardEntry` / `AgentIO` 四份 JSON Schema，见《系统架构设计》接口契约章节）；搭建仓库骨架与 docker-compose（PostgreSQL 16 + pgvector、Redis 7）；LLM Gateway 打通主备两个模型，完成统一调用与降级 |
| **W2** | 基于 LangGraph 实现 Planner → Retriever（SQL 取数）→ Analyst 串行链路；任务状态 Checkpoint 落 PostgreSQL；短期记忆接 Redis |
| **W3** | SQL 沙箱（只读连接 + 语句超时 + 行数上限）与 Python 沙箱（subprocess + CPU/内存/超时限制，**本期不做 gVisor 级隔离**）；接入知识库 RAG（bge-m3 + pgvector）；最小交互入口：REST 接口 + SSE 流式输出 |
| **W4** | 接入 Reviewer Agent（交叉校验）；构建 20 条评测用例并回归；缺陷修复；内部 Demo 评审与复盘 |

- **关键交付物**：
  - 可运行的 **单场景 Demo**（REST 提交自然语言分析需求 → 输出图表与结论报告）；
  - **4 份接口契约**（JSON Schema）与统一 Agent 基类、工具调用 SDK、模型网关 SDK；
  - 首版评测集（20 条）与成功率/时延基线报告；
  - 本地一键启动脚本（docker-compose）。
- **里程碑 M1（第 4 周末）**：Demo 评审通过，20 条用例端到端成功率 ≥ 80%，单任务端到端时延 ≤ 60 秒。

**W2 实测结果（2026-10-16）**——跑通需求「分析上月华东区销售额下滑的原因」：

- 端到端 **50.5 秒 / 10,304 token**（输入 2,435 / 输出 7,869）；
- **结论正确性**：模型基于沙箱真实查询结果独立算出的数字，与构造数据完全一致——
  华东区环比 **-20.85%**（295 万 → 233.5 万），主因线上数码 **-37.60%**（占总降幅 76.4%），
  门店渠道仅 **-1.95%**，数码退款率 4.19% → 10.54%；且明确声明数据不足以定位流量/价格等根因；
- 溯源链路完整：每条结论带 `model_inference` 与 `sql sha256` 引用。

**✅ D2 已定（原为待定）**——**`DEFAULT_MAX_TOKENS = 40,000`**。

关键发现：原默认值 200,000 **形同虚设**（实测最大仅 4 万，熔断永远不会触发，
等于没有保护）。按「实测最大 × 1.5 安全系数、向上取整到万」收紧为 40,000，
使任务级熔断真正具备兜底作用。已在 `.env` / `.env.example` 同步。

**已完成的调优：** SQL 修补上限由 3 次收紧为 2 次。依据：两类失败
（SQL 被数据库拒绝、归因判定数据不足）都在**下一次尝试**即被修复；
设到 3 次时唯一效果是造出最差离群点。复测最差 3 条：最差 166.6s → 101.6s，
token 40,600 → 12,196，成功率不变。

**分级路由（2026-10-16 落地）— P95 由 133.8 秒降至 76.3 秒（改善 43%），但未达 M1 目标**

动机即上面的根因：模型调用占全部墙钟耗时的 **99%**，而两个端点都是推理型模型。

**实现**：`gateway/router.py` 的 `ModelRouter` 按**调用点**分派到两个档位
（`reasoning` / `fast`），档位内各自带主备降级链；路由表是配置项（`LLM_ROUTING`），
改路由不用改代码。逐次调用明细挂在 `PipelineOutcome.call_records` 上，
评测报告会给出按调用点的成本与时延归因表。

**先量后改**——调用点归因（6 条用例）：

| 调用点 | 次数 | 单次 token | 单次耗时 | 占模型调用耗时 |
| :--- | --: | --: | --: | --: |
| `analyst_sql` | 10 | 3,869 | 20.9s | **58%** |
| `analyst_conclude` | 9 | 2,453 | 11.6s | 29% |
| `planner` | 6 | 1,756 | 7.7s | 13% |

反直觉发现：**「生成 SQL」比「归因」更贵**（20.9s vs 11.6s 每次）。原因是取数提示词
最长（含 schema、数据真实时间范围、指标口径、验收标准），推理型模型在长输入上
烧的思考 token 反而更多。这正证明了「按调用点而非按角色路由」的必要性。

**两次否定实验**（本次最有价值的产出，省下未来两次踩坑）：

| 实验 | 结果 |
| :--- | :--- |
| `planner` → fast | ❌ 核心用例 `core_decline_cause` 直接失败。它写的验收标准会传给取数环节，是**承重环节** |
| `analyst_conclude` → fast | ❌ 总耗时再降 31%，但核心用例同样失败。它确实是**真推理步骤** |

**最终路由表**：`planner` → reasoning；`analyst_sql` → **fast**；`analyst_conclude` → reasoning。

| 指标 | 路由前 | 路由后 | 变化 |
| :--- | :--- | :--- | :--- |
| 成功率 | 20/20 = 100% | **20/20 = 100%** | 不变 ✅ |
| P50 端到端时延 | 37.3 秒 | **29.6 秒** | −21% |
| P95 端到端时延 | 133.8 秒 | **76.3 秒** | **−43%** ❌ 仍超 60 秒 |
| 最大端到端时延 | 166.6 秒 | **79.8 秒** | −52% |
| 平均 Token/任务 | 10,925 | **6,897** | **−37%** |
| 最大 Token/任务 | 40,600 | **16,511** | **−59%** |

**⚠️ 验收结论：成功率 100%（远超 ≥90% 门槛）✅；但 P95 76.3 秒未达 60 秒目标 ❌，未完全达标。**

超时的 2 条用例（`east_store_flat` 79.8 秒、`south_stable` 76.3 秒）都触发了 SQL 修补轮，
产生 4 次模型调用而非 3 次。

**fast 档输出上限钳制（2026-10-16）— ✅ M1 时延目标达成，但成功率降至 85%**

分级路由后 P95 仍为 76.3 秒。继续查根因时**推翻了「取数提示词太长」的判断**：

| 输入长度 | 耗时 |
| :--- | :--- |
| 20 token | 2.7 秒 |
| 356 token | 5.4 秒 |
| 763 token（真实完整提示词） | 4.1 秒 |

本地端点对输入长度**几乎不敏感**（约 2.5–3 秒固定开销）。真正的主因是
**输出上限设太大，等于邀请模型无限思考**：

| max_tokens | 输出 | 思考 token | 耗时 |
| :--- | --: | --: | --: |
| 8192 | 599 | 453 | 10.7 秒 |
| 2048 | 117 | **0** | **4.5 秒** |

改动：`ModelRouter` 按档位钳制输出上限（fast 2048 / reasoning 8192），
调用方只能要求「不多于」本档上限。配套安全网：整条链都因 `finish_reason=length`
被截断时放宽一次重试——用**异常类型**判断「额度被吃满」与「供应商真挂了」，
不靠匹配错误文本。

顺带修掉两处正确性问题：LangGraph 的 4 张内部表占了表结构提示词约 70% 的字符
（681 → 242 字符，且可能诱导模型去查框架表）；两条把**正确答案判失败**的用例
（1.953% 四舍五入写作 2.0%；及一条过度指定的期望）。

**20 条验收（钳制后）与三轮对比：**

| 指标 | 分级路由前 | 仅路由 | **钳制后** | 相对路由前 |
| :--- | :--- | :--- | :--- | :--- |
| 成功率 | 20/20 = 100% | 20/20 = 100% | **17/20 = 85%** | ⚠️ 低于 90% 门槛 |
| P50 端到端时延 | 37.3 秒 | 29.6 秒 | **31.6 秒** | −15% |
| P95 端到端时延 | 133.8 秒 | 76.3 秒 | **40.6 秒** | **−70%** ✅ |
| 最大端到端时延 | 166.6 秒 | 79.8 秒 | **41.1 秒** | **−75%** |
| 平均 Token/任务 | 10,925 | 6,897 | **5,659** | **−48%** |
| 最大 Token/任务 | 40,600 | 16,511 | **8,951** | **−78%** |

> ### ✅ M1 时延目标达成
> P95 **40.6 秒 ≤ 60 秒**，且 20 条用例**无一超过 60 秒**（最慢 41.1 秒）。
>
> ### ⚠️ 成功率 85%，低于 90% 门槛
> 较仅路由时的 100% 有回退，这是钳制输出上限换来的代价。3 条失败用例的性质：

| 失败用例 | 性质 |
| :--- | :--- |
| `core_decline_cause` | SQL 未取到对比基期（未返回两月总额）。钳制后取数模型产出的查询变浅 |
| `east_category_digital` | **任务失败**：fast 模型连写两条坏 SQL 被数据库拒绝（`UNION` 列数不一致；SQL 尾部破坏沙箱的子查询包装） |
| `south_stable` | 模型把「稳定性」理解为需要**每日**数据算波动率，而数据是月度快照，遂判「数据不足」。技术上正确但未回答问题 |

**取舍结论**：时延与成功率在当前配置下相互牵制，本轮选择「保时延」。
要回到 100% 成功率，最直接的手段是把取数档上限从 2048 放宽（代价是时延回升）。
按本人指示本轮不再就此继续调优，**如实记录为遗留项**。

**已知的健壮性缺陷（未修）**：`SqlSandbox._wrap` 用子查询包装模型 SQL，
模型若产出尾部注释/不完整语句会破坏包装，报错信息也不易理解
（`east_category_digital` 的第 2 次失败即此）。修法是在包装前清理尾部注释并补齐换行。

**其他偏差：**

1. **Planner 与执行能力需对齐**：Planner 会产出多节点 DAG（如含 reviewer），
   而 W2 是固定串行链路。已对可执行节点集合做**硬约束**（仅 `retriever_1` / `analyst_1`），
   超范围直接报 `UNSUPPORTED_PLAN` 而非静默丢弃计划的一部分；
   动态执行任意 DAG 仍属 **W5** 范围。
2. **归因环节不得接触验收标准**：取数环节需要验收标准（否则不知要取什么维度与基期），
   但归因环节若知道期望答案会有迎合压力而编造数字，故其唯一输入是真实结果行。
   这条约束在评测中生效（`missing_data_honesty` 用例通过，未编造华北区数据）。

## 3.8 W3 交付详解（2026-10-16）

| 交付项 | 实现 | 验证方式 |
| :--- | :--- | :--- |
| Python 代码沙箱 | `tools/python.py`：容器后端（`--network none` / `--read-only` / 内存·CPU·进程数配额 / 非 root）+ 子进程降级（**降级时如实标注 isolation**） | 15 项测试证明**隔离真的生效**：容器内连不上外网、根文件系统只读、超内存被 OOM 杀死、matplotlib 能渲染中文标签 |
| 知识库 RAG | `rag/`：本地 fastembed（bge-small-zh-v1.5，512 维）+ pgvector，混合检索（向量分 + `pg_trgm` 关键词分线性加权） | 检索质量实测：问「退货率为什么上升」命中退货政策文档；问「能不能算日波动率」命中数据字典中明确说「不能」的那段 |
| 交互入口 | `api/`：FastAPI + REST + SSE，**节点级进度实时推送** | 端到端实测 45.4 秒 / 9,980 token，服务日志零异常；10 项接口测试 |

**RAG 的实际价值（实测印证）**

问「华东区 9 月线上退货率为什么大幅上升」，系统查数后结合《线上渠道退货政策调整通知》给出：
「8 月起线上退货政策口径调整（微瑕疵进入退货流程、免运费取消后只退款不退货计入退货金额），
可解释线上退货率跳升而**非门店或产品质量实质恶化**」，并用「线上跳升、门店稳定」的
渠道差异作为证据，同时明说「无法量化政策口径的具体贡献」。

**SQL 只能答「上升了」，RAG 才能答「为什么、以及这是不是真问题」。**

**关键约束**：背景资料只能用于解释原因，**不得把其中的数字当查询结果引用**（那是编造数据）。
该约束写进了取数与归因两个提示词。

**模型选型取舍**：架构原定 bge-m3（约 2.2GB），改用 bge-small-zh-v1.5（约 95MB / 512 维）——
本机 C 盘仅剩 2.8G。模型缓存放在项目内 `.model_cache/`（已 gitignore），不占系统盘；
经 hf-mirror.com 拉取（直连 HuggingFace 在本网络不可达）。

**环境约束（会影响后续所有下载，已实测）**

| 目标 | 状态 | 应对 |
| :--- | :--- | :--- |
| Docker Hub | ⚠️ 时通时断 | 曾致镜像构建失败；现恢复可达 |
| HuggingFace | ❌ 不可达 | 模型下载必须走 hf-mirror.com |
| PyPI | ✅ 可达 | 依赖安装正常 |

**未做（如实记录）**：交互入口无鉴权 / 限流 / CORS；任务状态是**进程内存储，重启即丢**
（属 W7 一并持久化）；Reranker 未启用；行级权限过滤随 RBAC 延后。

**W3 期间修掉的四个真实缺陷**

| # | 缺陷 | 性质 |
| :-- | :--- | :--- |
| 1 | `LLMMessage` 缺 `assistant()` 工厂方法 | 结构化输出的纠错重试**一进就崩**，该路径此前从未真正走通过 |
| 2 | 分块器拼接 overlap 尾巴时未把尾巴计入预算 | 产出超过 `chunk_size` 的块 |
| 3 | uvicorn 在 Windows 上**硬编码** ProactorEventLoop，而 psycopg 异步不支持 | 提前 `set_event_loop_policy` 完全无效；正确修法是覆盖 loop 工厂（`loop="asyncio:SelectorEventLoop"`） |
| 4 | SSE 补发历史事件被丢弃 | 任务已结束时直接返回、跳过了刚入队的缓冲事件，恰好废掉「缓冲」的整个意义 |

## 3.9 W4 评测回归（2026-10-16）

用例集由 20 条扩到 **24 条**：新增 4 条**知识库依赖用例**，设计原则是「**SQL 单独答不出来**」。

| 用例 | 为什么必须靠知识库 |
| :--- | :--- |
| `rag_refund_is_policy_not_quality` | 数据只显示退货率上升；能否解释成「政策口径变化而非质量恶化」只存在于政策文档 |
| `rag_region_definition` | SQL 里只有「华东」两个字，省市清单只在知识库 |
| `rag_daily_volatility_infeasible` | 数据是月度快照、算不了日粒度——这个可行性判断来自数据字典 |
| `rag_sep_promo_anomaly` | 9 月本是线上数码高峰，不升反降属异常——需要运营日历 |

**RAG 用例有牙齿（对照实验验证）**：清空知识库后 `rag_region_definition` **立即失败**
（未命中 `江苏` / `浙江` / `未检索到任何知识` / `知识库:region-definition`），重新灌库后恢复通过。
打分器同时检查**检索结果**（结构性证据）与**答案内容**——只查答案文本无法区分
「模型本来就知道」与「真的查了知识库」。

**24 条回归结果与三轮对比：**

| 指标 | 路由前 | 钳制后 | **本轮（W4 + RAG）** |
| :--- | :--- | :--- | :--- |
| 成功率 | 20/20 = 100% | 17/20 = 85% | **24/24 = 100%** ✅ |
| P50 端到端时延 | 37.3 秒 | 31.6 秒 | **30.8 秒** ✅ |
| P95 端到端时延 | 133.8 秒 | 40.6 秒 | **74.3 秒** ❌ |
| 最大端到端时延 | 166.6 秒 | 41.1 秒 | **83.4 秒** ❌ |
| 平均 Token/任务 | 10,925 | 5,659 | **8,903** |
| 最大 Token/任务 | 40,600 | 8,951 | **20,550** |

> **✅ 成功率 100%**，远超 M1 的 80% 门槛，也高于 90% 目标。
> **⚠️ P95 74.3 秒重新超过 60 秒**——3 条超时：`south_stable` 83.4s、`three_month_trend` 74.3s、
> `rag_sep_promo_anomaly` 62.9s。

**为什么时延回升了（本轮的关键发现）**：知识库把检索到的片段同时塞进**取数与归因两个
提示词**，输入变长、平均 token 从 5,659 升到 8,903，时延随之上升。

**但正是这个变化把成功率从 85% 拉回了 100%**：数据字典里「不能用该表计算月内日波动率」
这一条直接治好了 `south_stable`（它原先试图算日波动率而判定数据不足），
运营日历则治好了 `east_category_digital`。

**取舍结论**：RAG 用「时延」换「质量」，且质量收益明确、可归因到具体文档。
这再次印证：**时延与成功率在当前配置下相互牵制，单独优化任一项都会牺牲另一项。**

**下一步候选手段**（尚未实施，遵循「先量后改」）：

1. **压缩知识片段预算**：当前 4 段 × 400 字符，且在两个提示词里各出现一次——
   预计可省下可观输入 token；
2. **保内容、压形式**：`south_stable` 依赖的是「数据可行性说明」这类短事实，
   描述性内容可压、结论性内容不能压；
3. **降低 SQL 修补轮触发率**：3 条超时用例中至少一条触发了修补（token 达 20,550）。

## 3.10 W5 动态 DAG 引擎（2026-10-16）

**交付**：编排层从写死的 3 节点串行链路，改为由 Planner 产出的 SubtaskDAG
在运行时驱动构图与执行。

生产链路的 DAG 形态（实测产出）：

```
retriever_1(mode=metrics)   ─┐
                              ├─→ analyst_1
retriever_2(mode=knowledge) ─┘
```

**引擎是通用的**：能执行任意合法 DAG（链 / 菱形 / 三路扇出 / 两层树 / 多汇点），
由 `tests/test_pipeline_engine.py` 用**合成 DAG** 证明——生产链路只跑一种形状，
证明不了通用性。

**并行性用可测量的方式断言**：假 Agent 带人工延迟并记录调用区间，兄弟节点的时间
区间必须真实重叠，且总耗时显著小于串行。**"看起来是并行的"不算证据。**

### 关键设计决定

| 项 | 决定 | 理由 |
| :--- | :--- | :--- |
| Planner 位置 | 在图**之外**先跑 | 图结构依赖它的输出；契约也写明它是产出者而非节点 |
| 执行器 | 保留 LangGraph 的**构期动态构图** | 实测 1.2.15 支持由运行时数据决定 add_node/add_edge 再 compile()；保留 checkpoint 与未来的 `interrupt()` |
| 节点差异化行为 | 节点自带的 `inputs.mode` | 两路检索同角色不同分工；顺带把契约里**一直闲置**的 `SubtaskNode.inputs` 用起来 |
| 通用性边界 | 用**角色注册表**校验，不用固定 node_id | "Planner 能规划什么" = `build_agent_registry()` 登记了什么；新增角色只需登记一行 |

### 必须同时修的三个并发硬伤（都会被并行放大）

1. **state 字段无 reducer**——无 reducer 的字段是 `LastValue` channel，同一步内两个节点
   写入会直接抛 `InvalidUpdateError`。`node_outputs` / `blackboard` / `node_results`
   全部改为 `Annotated[T, reducer]`。
2. **`_absorb` 是读-改-写全量覆盖**——并行时会丢更新。改为**只返回本节点的增量**，
   由 reducer 合并。
3. **`_absorb` 按 role 三选一分发**——新角色的输出会被静默丢弃。改为通用的
   `node_outputs`，并去掉状态里所有按 role 硬编码的扁平字段，下游改从
   `depends_on` 声明的上游产物里取。

### W5 期间修掉的缺陷

| # | 缺陷 | 性质 |
| :-- | :--- | :--- |
| 1 | Planner 写 `inputs.mode`、Retriever 读 `retrieval_mode`，**键名不一致** | 两个检索节点都退化成 all 模式**重复检索**。单测没抓到是因为测试与实现用了同一个错键名——**由端到端冒烟发现** |
| 2 | 黑板 `written_by` 写死 `@0.1.0` | 与真实 Agent 版本不符（潜伏 bug），改用 `agent.labeled_version` |
| 3 | 黑板 key 写死 `analyst_1.report` / `retriever_1.*` | 多个同角色节点会互相覆盖，改为由 `inv.node_id` 派生 |
| 4 | 一处**间歇性** `AttributeError: 'str' object has no attribute 'get'` | 24 条回归中出现 1 次，复现未果。已把模糊异常换成**能定位的精确报错**（指明节点与实际类型），复发即可定位。**如实记录为未解项** |
| 5 | **并行在实测中退化成串行**——两个检索节点只是首尾相接，没有重叠 | 真实 Retriever 里全是**同步阻塞调用**（psycopg 同步查询、fastembed CPU 推理），把事件循环占住，另一路只能排队。引擎单测没抓到，是因为假 Agent 用 `await asyncio.sleep()`（真让出循环）。修法：阻塞工作走 `asyncio.to_thread`。修后时间线显示两路**同时启动**（[5.33, 5.44] 与 [5.33, 6.10]）。**由「SSE 事件里两个检索节点并行启动」这条验收标准抓到** |
| 6 | **知识库无命中时检索节点崩溃**（契约校验失败） | 契约要求 `status=ok` 的结果必须带 `sources`；「没命中」时一条都加不上 → 走 SQL/知识库都拿不到内容时，节点在 `ok()` 处抛 ValidationError，**挂掉整个任务**。修法：无命中时补一条「检索无命中」的来源记录（检索本身也是来源）。此前所有用例都能检索到内容，所以一直没暴露 |

### 24 条回归结果

## 3.11 W6 多 Agent 协同（2026-10-16/17）

**交付**：① Reviewer Agent（分析/文档任务**强制交叉校验**）；② Writer Agent + 第 2 场景
（报告/文档自动化）端到端跑通；③ 共享长期记忆（评审门槛后沉淀、跨会话检索）；
④ 黑板契约化（条目过冻结契约 + 版本号乐观锁 + 订阅可见性 + 变更事件）。

**契约零改动**：reviewer/writer 的枚举与黑板乐观锁语义在 W1 冻结契约里早已预留，
W6 只是把「契约语义」落成「实现」——这印证了 W1「契约先行」的收益。

### 关键设计决定

| 项 | 决定 | 理由 |
| :--- | :--- | :--- |
| 黑板变更通知 | **进程内事件通道**（on_event → SSE） | 单进程无跨进程订阅者；Redis Stream 移至多进程/扩员阶段（架构文档同步修订） |
| Reviewer 范围 | 分析/文档任务**强制必审** | 产品文档「强制交叉校验」是 R1 幻觉风险的主要缓解；代价见下方实测 |
| Reviewer 依赖 | 依赖图中其余**全部**节点 | 只依赖 analyst 时，验收标准引用的检索材料不可见 → 被记成 unmet → 误判 fail（实测抓到） |
| 长期记忆存储 | **独立表** `memory_entries`，不复用 `knowledge_chunks` | 评测的 RAG 回归按检索到的 knowledge 做结构性断言，混表会污染证据；语义与生命周期也不同 |
| 沉淀门槛 | 任务成功 + 存在 reviewer 且 verdict ≠ fail + 非「数据不足」 | 「被标记为可沉淀」的落点；门槛是纯函数并被单测穷举 |
| 记忆检索 | 只取 `status='validated'` 且未过期 | 被否决/未审的记忆对后续会话不可见 |
| Reviewer/Writer 档位 | reasoning | 与 planner 同为承重环节；实测 reviewer 单次均值 10,040 token / 35.3 秒 |

### W6 期间修掉的缺陷（两项只有端到端才能发现）

| # | 缺陷 | 性质 |
| :-- | :--- | :--- |
| 1 | **引擎：逐个 `add_edge(dep,node)` 是「任一上游完成即触发」** | reviewer 在 analyst 完成前提前执行一次、依赖齐了又执行一次。**由新加的黑板冲突检测当场抓到**（键已存在→冲突）。修法：列表形式连边（join 语义），并加单测钉住「跨层依赖只执行一次」 |
| 2 | 黑板条目**不合冻结契约** | `written_by` 是字符串、version 恒为 1、无乐观锁、缺 task_id/status/written_at——契约校验形同虚设。改为 `BlackboardEntry` 契约对象 + `blackboard_updates` 乐观锁（版本不符即拒绝） |
| 3 | Reviewer 依赖不足 + 缺 unverifiable 语义 | 验收标准引用检索材料但 reviewer 看不到 → 记 unmet → 误判 fail。修法：依赖全部上游；缺材料应记 `unverifiable` 而非 `unmet` |
| 4 | **输出上限 8192 对新推理模型不够** | 本地 `cn:deepseek-v4.1-flash` 某次调用思考消耗满 8192 仍无正文（空内容失败，随后兜底端点超时，任务失败）。推理档的「截断放宽重试」在 requested==cap 时不会触发，所以上限本身必须留足 → 扩至 16384 |
| 5 | **测试隔离缺陷：记忆测试 `clear()` 整表清空** | 跑一次 pytest 会把开发库真实沉淀的记忆全部抹掉（由序列值 56 vs 表内 0 行的矛盾查出）。修法：测试只用 `w6test-` 命名空间 + 探针标记，并验证「真实行在跑测试后幸存」 |
| 6 | `python -m multiagent.memory` 缺 `__main__` | 文档里的命令直接报错 |
| 7 | 观测缺口：节点失败时 `outcome.error` 不含节点名 | 已补上（现在能定位「哪个节点挂的」）。**未修并如实记录**：失败路径不保留已消耗 token 的记录（报告显示 0 token） |

## 3.12 W7 异常处理 + HITL 后端阻塞点 + 四大约束熔断（2026-10-17）

**交付**（路线图 W7 行 + M2 出口的「熔断可触发并正确转人工、HITL 阻塞点可拦截」）：
① **四大约束熔断**（`max_steps` / `max_tokens` / `max_retries` / `deadline`——此前
全部只有契约字段、没有实现）；② **节点级重试与超时**；③ **HITL 后端阻塞点**
（批准 / 驳回 / 改写）；④ **有界动态重规划**（`revision` 递增，`max_replans=1`）。

### 本轮拍板（未获答复，按推荐选项执行并留痕）

| 决策 | 选择 | 理由 |
| :--- | :--- | :--- |
| 重规划触发 | **仅节点重试耗尽 / `needs_replan`**；评审 fail 不返工 | 评审标准尚未按问题类型校准，返工会放大无效重跑（W6 有 7/27 条 fail verdict） |
| 条件分支 / 竞速 / 多 reviewer 仲裁 | **不进 W7**，归属改为 W8/扩员 | 冻结契约 v1.0.0 无条件分支载体；多 reviewer 需先定仲裁公式 + 引擎级同键冲突检测 |
| 熔断的「转人工」落点 | 任务终止于**稳定错误码** + `task_breaker_tripped` 事件 | 单租户没有审批队列；HITL 阻塞点只用于节点审批 |

### 语义落地（文档只说「熔断」，实现必须定义清楚）

- **「步」= 一次节点执行**（含重试的每次 attempt）；Planner 图外调用计 1 步、其 token 计入。
- **检查在节点启动前**：超限的节点不启动；单节点开销可能使总量略微越界（可接受边界）。
- **重试** = `min(节点 max_retries, 任务 max_retries)`，每次尝试带超时
  `min(任务超时, 节点 timeout_seconds)`，并计入步数；不可重试错误直接上抛。
- **HITL 三态**：批准 → 继续；驳回 → 独立终态 `rejected`（下游节点执行前短路，Agent 不运行）；
  改写 → 人工产物以**版本 +1** 写回黑板（写入者记 `system`、审批人记在来源 ref），下游用替换产物。
- **恢复**：`Command(resume=...)` + 同一 thread_id + **DAG 指纹校验**（拓扑变了明确拒绝——
  LangGraph 在拓扑变化时会静默丢弃暂停状态）。
- **重规划**：新 DAG 在独立 thread（`{task_id}:r{revision}`）从头执行，**不复用旧图状态**
  （复用需改写 checkpoint，明确不做）；重规划消耗计入任务级 steps/tokens/deadline。

### W7 期间修掉的缺陷

| # | 缺陷 | 性质 |
| :-- | :--- | :--- |
| 1 | **`saver.aget` 返回形状假设错误**（W5 遗留） | W5 的 `resume` 分支写 `snapshot.checkpoint[...]`，而 langgraph-checkpoint 4.3 的 `aget` 返回 checkpoint **dict**；**该分支从未真正走通**，W7 做 HITL 恢复时暴露。修法：dict / CheckpointTuple 双兼容 |
| 2 | **失败路径丢 token/节点**（W6 缺陷 7 根修） | 失败时从 checkpoint 取回部分结果，熔断计数与成本归因才有数据 |
| 3 | **Planner 把「内部通知」过度标为审批节点** | 文档通知用例在执行中暂停 → 评测侧加「自动批准」（模拟审批人，HITL 全链路纳入评测）+ 提示词收敛（仅对外发送/正式签发才标 true） |
| 4 | **`Command(goto=END)` 不压制静态边** | 实测驳回后下游仍会执行。改为「下游节点执行前看到驳回记录即短路」，Agent 不会运行 |

## 3.14 W9 安全基线（2026-10-20）

**交付**（路线图 W9 行：输入过滤 + 输出 DLP + API Key 简单角色权限；单租户，不做完整 RBAC+ABAC）：

1. **输入过滤**（`security/input_guard.py`）：
   - 6 类 Prompt Injection 规则（忽略既有指令、套取系统提示、角色劫持、绕过安全/沙箱、敏感词）；
   - 归一化先做 NFKC、去零宽字符、**汉字间空格折叠**、小写——大小写/全角/零宽/插空格不能绕过；
   - 输入中的身份证/手机号/银行卡/密钥**就地脱敏后放行**（避免把「贴数据做分析」的正常需求拒掉）；
   - API 提交前命中即 **400 `INPUT_BLOCKED`**（不建任务、不调模型）；编排层入口再兜底，
     CLI / 评测 / 直接调用同样生效。
2. **输出 DLP**（`security/dlp.py`）：
   - 身份证、手机号、银行卡（**Luhn 校验**，防误伤营收/订单数字）、`sk-`/`ghp_`/`AKIA`/JWT/私钥/`password:` 等；
   - 覆盖 API 结果、任务列表、SSE 事件、CLI 输出、**长期记忆沉淀**；
   - 422 校验错误去掉 `input` 字段，错误响应也不回显 PII。
3. **API Key + 简单角色**（`security/auth.py`）：`API_KEYS=key:role,...`，角色固定映射；
   启用鉴权但未配置 Key 时**启动失败**（fail closed）；审批人记 Key 指纹而非调用方自称。
4. **测试 290 → 320**：规则/脱敏/鉴权/权限/端到端（含 SSE query Key、422 不回显、记忆脱敏）。

**角色与权限**：

| 角色 | `tasks:read` | `tasks:submit` | `tasks:approve` |
| :--- | :---: | :---: | :---: |
| `viewer` | ✅ | ❌ | ❌ |
| `operator` | ✅ | ✅ | ❌ |
| `admin` | ✅ | ✅ | ✅ |

**验证**：

- 真实 API 冒烟：无 Key → 401；viewer 提交 → 403；注入 → 400 `INPUT_BLOCKED`；
  正常问题 → 202 → `ok`；结果经 DLP；
- 评测抽跑 6 条（分析 2 / 文档 2 / RAG 1 / 跨会话记忆 1，含记忆前置用例）：**6/6 通过**（安全层不影响打分）。

**明确取舍（SSE Key）**：浏览器 `EventSource` 不能自定义 Header，因此**只有** `/tasks/{id}/events`

**未做（如实记录）**：
