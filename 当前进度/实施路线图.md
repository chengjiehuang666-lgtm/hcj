## 3.1 总体策略、节奏与人力

**人力规模：1 人（全职）。无前端、无运维、无测试专职。**

由此推导出三条硬约束，它们决定了后面所有排期与范围：

1. **一切并行皆串行。** 原四线并行的总工期不能除以 4，必须按串行重新估算：阶段之间没有重叠，一个人一次只能推进一条线。
2. **不做平台工程。** 网关、消息总线、服务网格、多租户、集群化，对单人项目是纯负债而非资产，一律延后或砍掉（详见《系统架构设计》「实施范围声明」）。
3. **「每周可演示」不成立，改为「每里程碑可演示」。** 每个阶段预留 20% 缓冲——单人没有任何冗余人力，缓冲是唯一的抗风险手段。

仍然坚持的原则：垂直切片、契约先行（Schema 先冻结）、文档与代码一致、每个稳定功能立即提交。

| 阶段 | 周期 | 核心目标 | 出口标准（Definition of Done） |
| :--- | :--- | :--- | :--- |
| **阶段一 MVP 验证期** | Weeks 1–4 | 单场景单链路真的跑通 | 数据分析场景端到端可演示，20 条评测用例成功率 ≥ 80% |
| **阶段二 协同深化期** | Weeks 5–8 | 动态编排 + 多 Agent 协同 + 人工介入 | 2 个场景可用，成功率 ≥ 90%，熔断与 HITL 可触发 |
| **阶段三 可用化期** | Weeks 9–12 | 安全基线、可观测、可私有化单机部署 | 单机 docker-compose 可部署，冒烟通过，可回滚 |

> ⚠️ **相对原方案的出口标准下调**：原阶段三要求「K8s 高可用 + 多租户 + 灰度发布 + 99.9% 可用性 + 混沌测试」，这是 3–4 名专职工程师一个季度的工作量，单人不可达，**已整体移出本期范围**。若该目标不可让步，本项目需扩员至 3–4 人，或周期拉长至 20 周以上。

## 3.2 阶段一：MVP 验证期（Weeks 1–4）

- **目标**：用最小链路验证「规划 → 取数 → 分析 → 评审」的技术可行性，打通模型网关、LangGraph 编排、工具调用与最小交互入口。
- **范围收敛**：只做「数据分析流水线」1 个场景；只接入 1 个主模型 + 1 个备模型；工具只开放 SQL 查询、Python 沙箱、知识库检索 3 项。

### 周计划

| 周次 | 关键任务 |
| :--- | :--- |
| **W1** | **先冻结接口契约**（`TaskEvent` / `SubtaskDAG` / `BlackboardEntry` / `AgentIO` 四份 JSON Schema，见《系统架构设计》接口契约章节）；搭建仓库骨架与 docker-compose（PostgreSQL 16 + pgvector、Redis 7）；LLM Gateway 打通主备两个模型，完成统一调用与降级 |
| **W2** | 基于 LangGraph 实现 Planner → Retriever（SQL 取数）→ Analyst 串行链路；任务状态 Checkpoint 落 PostgreSQL；短期记忆接 Redis |
| **W3** | SQL 沙箱（只读连接 + 语句超时 + 行数上限）与 Python 沙箱（subprocess + CPU/内存/超时限制，**本期不做 gVisor 级隔离**）；接入知识库 RAG（bge-m3 + pgvector）；最小交互入口：REST 接口 + SSE 流式输出 |
| **W4** | 接入 Reviewer Agent（交叉校验）；构建 20 条评测用例并回归；缺陷修复；内部 Demo 评审与复盘 |

- **关键交付物**：
  - 可运行的 **单场景 Demo**（REST 提交自然语言分析需求 → 输出图表与结论报告）；
  - **4 份接口契约**（JSON Schema）与统一 Agent 基类、工具调用 SDK、模型网关 SDK；
  - 首版评测集（20 条）与成功率/时延基线报告；
  - 本地一键启动脚本（docker-compose）。
- **里程碑 M1（第 4 周末）**：Demo 评审通过，20 条用例端到端成功率 ≥ 80%，单任务端到端时延 ≤ 60 秒。

## 3.3 阶段二：多 Agent 协同深化期（Weeks 5–8）

- **目标**：从固定串行链路升级为动态 DAG 编排，补齐多 Agent 协作、共享长期记忆、异常处理与人工介入，并落地第二个业务场景。
- **范围**：引入 Orchestrator 动态调度（进程内 asyncio，**本期不引入 Kafka**）、长期记忆、Reviewer/HITL；新增第 2 个场景（建议「文档自动化」，链路最轻）。

### 周计划

| 周次 | 关键任务 |
| :--- | :--- |
| **W5** | Orchestrator 动态 DAG 引擎：Planner 产出子任务图、条件分支、并行节点（asyncio 并发调度）；节点就绪度推进与依赖解析 |
| **W6** | 共享长期记忆（pgvector 混合检索：bge-m3 向量 + BM25 + Reranker 精排）与黑板订阅机制（含条目版本号乐观锁）；新增第 2 个场景所需 Agent |
| **W7** | 异常处理体系：重试、超时、降级、动态重规划；HITL 人工审批**后端阻塞点**（批准/驳回/改写，UI 延后）；`max_steps`/`max_tokens`/`max_retries`/`deadline` 四大约束熔断 |
| **W8** | 第 2 个场景联调；多 Agent 交叉校验；评测集扩至 50 条（每场景 ≥ 20 条）；基础压测（单机并发瓶颈定位） |

- **关键交付物**：
  - **动态 DAG 调度引擎**（并行编排、条件分支、重规划、断点续跑）；
  - **异常处理与人工介入机制**（重试/熔断 + HITL 后端阻塞点）；
  - 长期记忆与知识库管理（含来源标注 `source/timestamp/confidence`、权限过滤雏形）；
  - 2 个场景可演示版本 + 扩充评测集与压测报告。
- **里程碑 M2（第 8 周末）**：2 个场景可用，任务成功率 ≥ 90%，熔断可触发并正确转人工，HITL 阻塞点可拦截。

## 3.4 阶段三：可用化期（Weeks 9–12）

- **目标**：达到「可私有化单机部署、可交付给首批用户试用」的水准，**而非原方案的生产级高可用**。
- **范围**：安全基线（输入过滤、输出脱敏、访问控制）、可观测（结构化日志、成本计量）、性能基线校准、回归测试、部署与回滚。

### 周计划

| 周次 | 关键任务 |
| :--- | :--- |
| **W9** | 安全基线：输入侧的敏感词与 Prompt Injection 规则过滤；输出侧 DLP 正则脱敏（身份证/手机号/银行卡/密钥）；API Key + 简单角色权限（单租户，不做 RBAC+ABAC 完整模型） |
| **W10** | 可观测：结构化日志、`task_id` 贯穿网关→编排→Agent→模型→工具、Token 与成本计量（按任务/Agent 统计） |
| **W11** | **压测并校准性能基线**（并发路数、QPS、Token 单任务成本上限——这时才有真实数据可填，替换本文档中所有「待定」项）；全量回归测试与修复 |
| **W12** | 三份文档收口；一键部署脚本与配置模板；**回滚演练**（基于 Git 标签）；编写最小运维说明 |

- **关键交付物**：
  - 安全基线实现与测试用例；
  - 可观测日志与成本计量看板（命令行/简单页面即可）；
  - **压测报告与性能基线**（填充本文档全部「待定」项）；
  - 单机部署包、回滚脚本、运维说明。
- **里程碑 M3（第 12 周末）**：以 `docker-compose` 在本机/单台服务器私有化部署成功，冒烟测试通过，可一键回滚到上一稳定版本。

> **原 M3 中的「核心接口可用性 ≥ 99.9%、多租户隔离、5%→20%→全量灰度发布、混沌/容灾测试」均不在本期范围。** 这些需要专职运维与多人值守，属于下一阶段（需扩员）的目标。

**W2 实测结果（2026-10-16）**——跑通需求「分析上月华东区销售额下滑的原因」：

- 端到端 **50.5 秒 / 10,304 token**（输入 2,435 / 输出 7,869）；
- **结论正确性**：模型基于沙箱真实查询结果独立算出的数字，与构造数据完全一致——
  华东区环比 **-20.85%**（295 万 → 233.5 万），主因线上数码 **-37.60%**（占总降幅 76.4%），
  门店渠道仅 **-1.95%**，数码退款率 4.19% → 10.54%；且明确声明数据不足以定位流量/价格等根因；
- 溯源链路完整：每条结论带 `model_inference` 与 `sql sha256` 引用。

**评测基线（2026-10-16，20 条用例，`deepseek/deepseek-flash`）**

用例集见 `src/multiagent/eval/cases.py`，期望值**由数据库实测算出**而非目测；
打分器本身有 12 项测试（打分器不准，基线就是假的）。

| 指标 | 实测 | M1 目标 | 结论 |
| :--- | :--- | :--- | :--- |
| 成功率 | **20/20 = 100%** | ≥ 80% | ✅ 达标 |
| P50 端到端时延 | **37.3 秒** | ≤ 60 秒 | ✅ |
| P95 端到端时延 | **133.8 秒** | ≤ 60 秒 | ❌ **未达标** |
| 最大端到端时延 | 166.6 秒 | ≤ 60 秒 | ❌ |
| 平均 Token/任务 | 10,925 | — | — |
| 最大 Token/任务 | 40,600 | — | — |

长尾：**6/20 用例超过 60 秒**。

**✅ D2 已定（原为待定）**——**`DEFAULT_MAX_TOKENS = 40,000`**。

关键发现：原默认值 200,000 **形同虚设**（实测最大仅 4 万，熔断永远不会触发，
等于没有保护）。按「实测最大 × 1.5 安全系数、向上取整到万」收紧为 40,000，
使任务级熔断真正具备兜底作用。已在 `.env` / `.env.example` 同步。

**已完成的调优：** SQL 修补上限由 3 次收紧为 2 次。依据：两类失败
（SQL 被数据库拒绝、归因判定数据不足）都在**下一次尝试**即被修复；
设到 3 次时唯一效果是造出最差离群点。复测最差 3 条：最差 166.6s → 101.6s，
token 40,600 → 12,196，成功率不变。

**❗ 遗留问题（转入 W3/W4）：P95 时延未达 M1 目标**

根因不是编排逻辑，而是**两个可用端点都是推理型模型**：连「生成一条 SQL」
这种机械步骤也要消耗 2,000–4,000 个思考 token，导致单次调用就可能耗时 40–80 秒。
这与《系统架构设计》2.2.4「分级路由」的结论一致。

对策（W3/W4 落地）：**简单的取数与抽取步骤改用非推理小模型**。
现有候选是本地 `glm-5.3` 端点——实测为非推理模型（思考 token = 0），
一次简单调用仅 3.39 秒 / 87 token，比推理型低一到两个数量级。

**其他偏差：**

1. **Planner 与执行能力需对齐**：Planner 会产出多节点 DAG（如含 reviewer），
   而 W2 是固定串行链路。已对可执行节点集合做**硬约束**（仅 `retriever_1` / `analyst_1`），
   超范围直接报 `UNSUPPORTED_PLAN` 而非静默丢弃计划的一部分；
   动态执行任意 DAG 仍属 **W5** 范围。
2. **归因环节不得接触验收标准**：取数环节需要验收标准（否则不知要取什么维度与基期），
   但归因环节若知道期望答案会有迎合压力而编造数字，故其唯一输入是真实结果行。
   这条约束在评测中生效（`missing_data_honesty` 用例通过，未编造华北区数据）。

# 4. 风险评估与应对

> 本节概率/影响栏已按**单人全职**重新评级。原方案按 4 线团队评估，与现状不符。

| # | 风险点 | 影响 | 概率 | 应对策略（具体可执行） |
| :--- | :--- | :--- | :--- | :--- |
| R1 | **大模型幻觉/结果不稳定**，分析结论或代码出错 | 高 | 高 | Reviewer Agent 强制交叉校验并要求证据引用；结构化输出 + Schema 校验；关键结论必须可回溯到来源数据；用评测集做版本回归；高风险节点 HITL 签发；置信度低于阈值自动补检索或转人工 |
| R2 | **编排死循环、步数膨胀导致 Token 成本失控** | 高 | **高**（原为中） | 每任务强制 `max_steps/max_tokens/max_retries/deadline` 熔断；语义缓存命中重复问题；小模型处理分类抽取、强模型仅用于规划推理；单人无人盯成本，熔断从「优化项」升级为**必需项**，W4 必须落地并定 D2 |
