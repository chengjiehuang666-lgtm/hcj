## 2.2 核心组件说明

### 2.2.1 调度中心（Orchestrator）

- **职责**：任务路由分发、DAG 状态推进、并行/串行编排、冲突解决、异常重规划、人工节点触发。
- **实现方式**：基于 **LangGraph 的图状态机（StateGraph）** 作为主编排内核。每个节点是一个 Agent 或工具调用，边表达依赖与条件分支；利用 LangGraph 的 **Checkpointer** 将图状态持久化到 PostgreSQL，支持任务暂停、断点续跑、时间旅行调试（重放/回滚）。
- **路由分发**：Planner 产出的 DAG 经校验后，由 Orchestrator 按节点就绪度向 Kafka 投递子任务；同层无依赖节点并行执行，竞速（Race）场景取最快合格结果。
  > **已实现（W5，2026-10-16）**：**引擎已按 DAG 在运行时驱动构图与执行**，但投递介质不是 Kafka
  > 而是**进程内 LangGraph**（单机部署下 Kafka 已被裁掉，见「实施范围声明」）：
  > Planner 在**图之外**先跑产出 DAG → 按 `dag.nodes` 逐个 `add_node`、按 `depends_on` 连边 →
  > `compile()` 后执行。同层无依赖节点由 LangGraph 在**同一个 superstep 内并发执行**。
  >
  > 三条并发硬约束（已在代码里落实并写进注释）：state 的并发字段必须带 reducer
  > （否则同一步内两节点写同一键会抛 `InvalidUpdateError`）；节点函数只能返回**增量**
  > （读旧状态再全量写回会丢更新）；**不按 role 硬编码状态字段**（会让新角色的输出被静默丢弃）。
  > 引擎通用性（链 / 菱形 / 三路扇出 / 两层树 / 多汇点）由合成 DAG 单测证明。
  > **已修复（W6，2026-10-16）**：连边必须用**列表形式**（join 语义）。逐个
  > `add_edge(dep, node)` 在 LangGraph 里是「任一上游完成即触发」——依赖跨层时下游会
  > 提前执行一次、依赖齐了又执行一次（reviewer 节点实测如此）。该缺陷由黑板冲突检测
  > 当场抓到，并有单测钉住「跨层依赖只执行一次」。
  > **竞速（Race）与条件分支尚未实现**，属 W7。
- **冲突解决**：多 Agent 结论冲突时，采用「Reviewer 仲裁 + 证据引用数 + 置信度」加权裁决；仍不可判定则升级人工，不静默二选一。
  > **已实现（W6）**：Reviewer Agent 已交付——逐条核对上游验收标准与证据（met / unmet /
  > unverifiable）、按严重度分级问题、产出 verdict（pass / pass_with_issues / fail），
  > 并以黑板乐观锁把上游条目流转为 validated / rejected。**「多结论仲裁加权」与
  > 「升级人工」仍属 W7**（需条件分支与 HITL）。
- **熔断保护**：每个任务携带 `max_steps`、`max_tokens`、`max_retries`、`deadline` 四大约束，由 Orchestrator 统一计数，超限即熔断。

### 2.2.2 共享记忆库（Shared Memory）

采用**三层记忆 + 单一黑板**架构，状态外置、读写分离：

| 记忆层级 | 载体 | 生命周期 | 内容 | 一致性策略 |
| :--- | :--- | :--- | :--- | :--- |
| **工作记忆（短期）** | Redis + LangGraph Checkpoint | 单次任务 | 中间变量、步骤状态、DAG 运行态 | 任务内强一致，TTL 过期 |
| **黑板（Blackboard）** | Redis Hash/Stream + PG 落盘 | 单次任务 | 各 Agent 共享产物，支持订阅通知 | 条目级版本号（乐观锁） |
| **长期记忆** | **本期：pgvector（与 PostgreSQL 同实例）**；规模化后迁 Milvus | 跨会话持久 | 事实、用户偏好、历史结论、知识条目 | 带来源、时间、密级；可删除/更正 |

> **黑板层已按契约落地（W6，2026-10-16）**：条目不再是与契约形状相近的手写 dict，
> 而是按 `BlackboardEntry` 构造（task_id / key / version / written_by / written_at /
> status / sources）。**覆盖写入走条目级乐观锁**：写入方提交读到的 version，
> 版本不符或条目不存在一律拒绝（`BLACKBOARD_CONFLICT`），绝不静默覆盖。
> 「订阅」的落地形态是**依赖驱动**——下游节点按 `depends_on` 获得上游条目与来源明细，
> `AgentInvocation.visible_blackboard_keys` 从闲置字段变为真实填充；变更通知走
> 进程内事件通道（`blackboard_written` 事件 → SSE）。黑板仍是**任务内**介质，
> 随任务结束而止（跨会话沉淀见长期记忆）。

- **写入**：Agent 产物先经 Schema 校验与 Reviewer 抽检，再写入黑板；被标记为「可沉淀」的结论经清洗后向量化入长期记忆。
  > **已实现（W6，2026-10-16）**：产物按冻结契约构造黑板条目；Reviewer 逐条核对后
  > 以条目级乐观锁把上游条目流转为 validated / rejected（draft → 终态）。
  > **长期记忆的写入门槛**（即「被标记为可沉淀」的落点，纯函数、单测穷举）：
  > 任务成功 + 存在 Reviewer 且 verdict ≠ fail + 结论非「数据不足」；
  > 沉淀为 best-effort，失败只记录不拖垮任务。
- **检索**：长期记忆采用「向量召回 + 关键词 BM25 混合检索 + Reranker 精排」，返回结果必须携带 `source / timestamp / confidence`，并按用户数据权限做行级过滤。
  > **已实现（W6 长期记忆；知识库实现见《实施路线图》3.8）**：长期记忆为**独立表**
  > `memory_entries`（与知识库分表——知识库是外部文档、记忆是任务产物，且混表会污染
  > 评测按 `knowledge` 做的结构性断言）。当前是「向量 + `pg_trgm` 关键词」的
  > **线性加权融合**（两路分都已归一化到 [0,1]，比 RRF 更直观且便于按语料调权重）；
  > **检索只返回 `status='validated'` 且未过期的条目**（被否决/未审的记忆不回流），
  > 回灌提示词时标注为「历史结论」并写明**不得作为本次数据证据**。
  > **Reranker 尚未启用**（先量后改：现有 RAG 回归全过，无排序质量证据支持引入）。
  > 行级权限过滤随 RBAC 延后。
- **遗忘与合规**：支持按用户/数据源删除（受 GDPR/个保法的删除权）、TTL 自动过期、记忆条目审计，避免错误记忆永久污染。
  > **部分落地（W6）**：TTL 字段与检索期过期过滤、`status` 生命周期（draft /
  > validated / rejected / superseded）已实现；**删除权与审计随 W9**。

### 2.2.3 通信总线（Communication Bus）

> **本期实现说明：** 单人 + 单机部署下，Kafka / gRPC / A2A **均不引入**。子任务调度使用**进程内 asyncio 并发**，Agent 之间以黑板（PostgreSQL + 图状态 Checkpoint）作为唯一交换介质。下表为规模化目标形态，待服务拆分或扩员后启用。
>
> 这一取舍的直接理由：单机部署没有削峰、跨机房、事件回放的实际需求，Kafka 带来的运维成本（集群、分区、消费组、监控）远超其收益，对单人项目是纯负债。
>
> **修订（W6，2026-10-16）：黑板变更通知改用进程内事件通道**（`on_event` → SSE），
> **Redis Stream 移至多进程/扩员阶段**。理由与砍 Kafka 同一逻辑：单进程下发布方与
> 订阅方在同一个事件循环里，没有任何跨进程订阅者——引入 Redis Stream 只增加一个
> 演示不出价值的运行部件。事件通道故障被显式吞掉（进度是观测手段，不是业务本身）。

同步与异步分离，按场景选型：

| 通信方式 | 技术 | 适用场景 | 关键机制 |
| :--- | :--- | :--- | :--- |
| **异步事件流（主）** | **Kafka**（**本期不引入**，见上方说明） | 子任务分发、Agent 解耦、削峰、事件回放 | 按 `task_id` 分区保证同任务有序；消费者组弹性扩缩；至少一次投递 + 幂等消费 |
| **同步调用** | **gRPC** | Orchestrator 对 Planner/Reviewer 的实时短调用、内部服务间高性能通信 | Protobuf 契约、超时/重试/熔断（istio） |
| **轻量即时消息** | Redis Stream（**未启用**，移至多进程阶段，见上方修订） | 黑板变更通知、HITL 实时推送、低延迟协作 | 消费组 + 消息确认；本期由进程内事件通道替代 |
| **Agent 互操作** | **A2A（Agent2Agent）/ JSON-RPC over HTTP** | 跨团队/外部 Agent 能力互通、标准化 Agent Card 发现 | 任务对象（Task）生命周期、制品（Artifact）交换 |
| **工具接入** | **MCP（Model Context Protocol）** | Agent 对接外部工具与上下文资源 | 标准化 tools/resources/prompts，工具白名单 |

- **状态同步**：以「事件溯源（Event Sourcing）」为唯一事实源——所有状态变更产生不可变事件写入 Kafka 与审计库，当前状态由事件回放得出；任一副本重启后依据 Checkpoint + 事件追平，杜绝多副本状态不一致。
- **幂等与补偿**：每个子任务携带全局幂等键 `task_id + node_id + attempt`；写操作天然幂等；跨工具的长事务采用 **Saga 模式 + 补偿动作**，失败可回滚已执行步骤。

### 2.2.4 大模型网关（LLM Gateway）

- 统一 OpenAI 兼容接口，后端接入 GPT/Claude 等海外模型与 DeepSeek、Qwen、豆包等国产模型及私有化部署模型。
- 提供：负载均衡、供应商健康检查、自动重试与熔断、流式转发、Token 与成本计量、Prompt 模板与版本中心、敏感词前置拦截、全量请求落盘（加密）用于审计与回放。

**分级路由（已实现，2026-10-16）**

按**调用点**（而非仅按 Agent 角色）把请求分派到不同档位的模型。之所以要细到调用点：
Analyst 的两次调用性质完全不同——「生成 SQL」是机械翻译，「归因」是真推理，
这正是最该区分的地方。

| 档位 | 用途 | 默认端点 |
| :--- | :--- | :--- |
| `reasoning` | 复杂规划与归因、评审、写作 | 推理型模型（W6 起为本地 `cn:deepseek-v4.1-flash`，备选本地 glm-5.3） |
| `fast` | 机械步骤：生成 SQL、抽取、分类 | 本地非推理型端点（glm-5.3） |

档位内部各自带主备降级链；路由表来自配置（`LLM_ROUTING`），改路由不需要改代码。

当前路由表与**实测依据**（20 条评测基线的调用点归因，见《实施路线图》3.7）：

| 调用点 | 档位 | 依据 |
| :--- | :--- | :--- |
| `planner` | reasoning | 占模型调用耗时 13%。它写的验收标准会传给取数环节，**切 fast 后核心用例直接失败**，故必须留在推理档 |
| `analyst_sql` | **fast** | 占模型调用耗时 **58%**（单次 20.9 秒 / 3,869 token）且是纯机械翻译。切 fast 后单次降至 11.3–13.9 秒 / 1,738 token |
| `analyst_conclude` | reasoning | 占 29%。**切 fast 后核心用例失败**——它确实是真推理步骤，不能省 |
| `reviewer` | reasoning（W6 新增） | 评审是承重环节（判定「能不能采信」并决定记忆沉淀），与 planner 同类；单次均值 8,005 token / 39.4 秒，**是 W6 新增成本的主体** |
| `writer` | reasoning（W6 新增） | 成文质量直接是交付物本身；实测文档任务单次 4.5–8.6k token |

> **一个反直觉的实测结论**：在上述基线里，「生成 SQL」比「归因」更贵
> （单次 20.9 秒 vs 11.6 秒）。原因是取数提示词最长（含 schema、数据真实时间范围、
> 指标口径、验收标准），推理型模型在长输入上烧的思考 token 反而更多。
> 这印证了「按调用点而非按角色路由」的必要性。
>
> **供应商切换（W6 收尾，记录在案）**：云端 deepseek 余额耗尽（HTTP 402）后，
> reasoning 档主模型切换为**本地端点部署的 `cn:deepseek-v4.1-flash`**（备选本地
> glm-5.3）。**切换只改了 `.env`，没有改一行路由代码**——这是网关抽象与
> 「路由表即配置」的直接收益。备选端的真实质量边界同时被观测到：本地 glm-5.3
> 在文档类任务的**规划**上不可靠（产出 node_id 与 role 不一致的畸形 DAG，
> 被规划门禁拦下），故它适合作为快速档/兜底，不适合承担规划与归因。
>
> **尚未实现**：按任务标签自动选模、语义缓存。二者属后续版本，当前路由表是静态配置。

### 2.2.5 工具执行沙箱（Tool Sandbox）

- Agent 生成的代码/SQL 在隔离沙箱执行：容器级隔离（gVisor / 容器 NetworkPolicy 禁外网白名单）、只读根文件系统、临时可写卷、CPU/内存/超时配额、无持久凭证。
- 工具按最小权限授权，高危工具（删改数据、外发、支付）强制二次确认与 HITL。
- 所有工具调用记录入参、出参、执行者与结果，供审计与重放。

### 2.2.6 安全中心（Guardian，横切所有层）

- **认证授权**：OIDC/OAuth2 统一认证；RBAC 管角色、ABAC 管数据属性（密级/部门/owner），Agent 以其「服务身份 + 发起人身份」双重继承权限，禁止越权访问数据。
- **输入过滤**：在网关与 RAG 召回两道关口做 Prompt Injection、越权指令、敏感内容检测；外部检索内容以「不可信数据」隔离标注，禁止其中的指令被执行。
- **输出审计**：结构化输出校验 + DLP 数据防泄漏（身份证/手机号/银行卡/密钥/财务数字正则与模型双识别）+ 脱敏后外发；高风险输出强制 HITL。
- **数据隐私**：传输 TLS 1.3、存储 AES-256、密钥由 Vault 管理；支持租户级数据隔离、私有化/离线部署、数据留存与删除策略、操作审计日志只增不改。
- **供应链安全**：第三方工具/MCP Server 白名单与签名校验，容器镜像扫描，最小镜像与非 root 运行。

## 2.3 技术栈选型

### 大模型层
- **主力模型（多供应商可切换）**：DeepSeek-R1/V3、Qwen3、豆包 Doubao（推理与中文业务），GPT/Claude（复杂规划与代码，按合规与网络条件选用）；私有化兜底采用 Qwen/DeepSeek 开源权重本地部署。
- **Embedding**：**本期用 `BAAI/bge-small-zh-v1.5`（512 维，模型约 95MB）**；规模化后再换 bge-m3（1024 维、稠密+稀疏向量）。**Reranker**：bge-reranker-v2（本期未启用）；**轻量分类**：Qwen 小尺寸模型。
  > **MVP 取舍说明（2026-10-16）**：架构原定 bge-m3，但其模型文件约 2.2GB，而本机 C 盘仅剩 2.8G。
  > bge-small-zh-v1.5 对本项目语料规模足够，实测语义区分度正常（相关句余弦相似度显著高于无关句）。
  > 这与「MVP 用 pgvector、规模化再上 Milvus」属同一类取舍。
  > **换模型须同步修改 `knowledge_chunks.embedding` 的维度并重新灌库。**
  > embedding 走**本地** fastembed（ONNX 运行时）——检索每次都要用，本地无按次成本、
  > 不受供应商可用性影响；模型经 hf-mirror.com 拉取（直连 HuggingFace 在本网络不可达），
  > 缓存在项目内 `.model_cache/`（已 gitignore），不占系统盘。
- **网关**：**自研**统一 LLM Gateway（`gateway/`）。已实现供应商无关抽象、主备降级、
  分级路由与逐次调用成本归因；**不引入 LiteLLM**——现有栈已足够，且自研便于把
  路由表做成配置项。

### Agent 框架选型（三者分工，非互斥）

| 框架 | 特性 | 在本项目中的定位 |
| :--- | :--- | :--- |
| **LangGraph** | 图状态机、Checkpoint 持久化、HITL、流式、可重放，工程化程度高 | **主编排内核**：承载 Orchestrator 与生产级 DAG 工作流 |
| **AutoGen** | 对话驱动多 Agent、GroupChat、人机协作，适合开放式协同探索 | 用于「多 Agent 辩论/评审」与需要自由对话协商的子环节 |
| **CrewAI** | Role/Task/Crew 角色化建模，上手快、业务流程表达直观 | 用于新业务场景的快速原型（POC）验证，成熟后迁移到 LangGraph |

### 后端框架与语言
- **核心服务**：Python 3.11 + **FastAPI**（Agent 与编排生态，异步）；高并发网关/渠道路由用 **Go**（Gin/gRPC）补充。
- **RPC 契约**：gRPC + Protobuf；对外 REST 由 grpc-gateway / FastAPI 暴露。
- **任务调度**：LangGraph Runtime + Kafka 消费者；定时任务用 Celery beat / 自研 Scheduler。

### 数据与中间件
- **关系/元数据库**：PostgreSQL 16（任务、DAG、Checkpoint、权限、审计索引）。
- **缓存/会话/黑板**：Redis 7（Cluster 模式）。
- **向量数据库**：**本期用 pgvector**（与 PostgreSQL 同实例，省一个中间件）；规模化后再平滑迁至 Milvus。
- **消息队列**：**本期不用 Kafka**，以 asyncio 进程内调度 + Redis Stream 通知替代；服务拆分后再引入 Kafka。
- **对象存储**：MinIO（产物文件、图表、文档、请求留档）。
- **知识图谱（可选）**：Neo4j，用于复杂实体关系与根因分析场景，非 MVP 必需。
- **密钥管理**：**本期用 `.env` + `.gitignore` 兜底**（`*.key`/`*.pem`/`secrets/`/`.env*` 已配置为禁止提交）；Vault 延后。

### 基础设施与可观测
- **运行时**：**本期 Docker + docker-compose 单机**；Kubernetes + HPA（按队列长度/CPU 弹性扩缩 Agent Worker）为规模化目标形态。
- **服务网格**：**本期不引入**；Istio（mTLS、流量治理、熔断、灰度）为规模化目标形态。
- **监控指标**：Prometheus + Grafana（成功率、延迟、Token 成本、队列堆积、工具失败率）。
- **日志**：Promtail/Loki + 审计专用只增存储。
- **链路追踪**：OpenTelemetry（以 `task_id` 贯穿网关→编排→Agent→模型→工具全链路）。
- **IaC 与流水线**：Terraform + GitLab CI/GitHub Actions（代码扫描、镜像构建、自动化测试、灰度发布）。
- **质量保障**：LangSmith / 自研评测平台做 Prompt 与链路版本的离线评测、回归与灰度对比。

### 前端
- **前端**：**本期只做 REST + SSE 极简入口**（无独立前端工程）；完整形态为 React 18 + TypeScript + Vite + **React Flow**（DAG 可视化），图表 ECharts，支持 SSE/WebSocket 流式输出与审批待办。

### 部署形态
- **本期默认**：**docker-compose 单机私有化部署**（满足数据不出域，无需 K8s）；
- **规模化目标形态**：Kubernetes 私有化部署，提供 Helm Chart（生产）；
- **多租户**：**本期不做**，单租户部署；逻辑隔离（命名空间 + 行级策略 + 向量分区）为扩员后目标。

## 2.5 接口契约（Interface Contracts）

契约先行是本项目的核心纪律：**Schema 先冻结，再写实现**。所有 Agent、工具、编排节点之间的数据都通过下表中的契约传递，任何一方不按契约产出即视为失败并退回重做（见《产品需求》1.3 协作机制约定）。

契约文件位于 `架构设想/接口契约/`，格式为 JSON Schema（draft 2020-12）。

| 契约 | 文件 | 作用 | 优先级 |
| :--- | :--- | :--- | :--- |
| **TaskEvent** | `task_event.schema.json` | 外部渠道消息归一化后的标准任务事件，是进入编排层的唯一入口结构 | MVP 必需（W1） |
| **SubtaskDAG** | `subtask_dag.schema.json` | Planner 输出的子任务图；Orchestrator 据此调度，节点含输入输出契约与验收标准 | MVP 必需（W1） |
| **BlackboardEntry** | `blackboard_entry.schema.json` | 黑板条目；所有 Agent 的唯一交换介质，含版本号乐观锁与来源溯源 | MVP 必需（W1） |
| **AgentIO** | `agent_io.schema.json` | 统一 Agent 调用契约（`AgentInvocation` / `AgentResult`），任意专家 Agent 都必须实现 | MVP 必需（W1） |
| **AgentCard** | 待定 | A2A 风格的能力声明，用于对外 Agent 互通与发现 | 延后至阶段二/三 |

**三条贯穿所有契约的约定：**

1. **全局标识**：所有契约必带 `task_id`（UUID）与 `schema_version`；子任务级消息另带 `node_id` 与 `attempt`，三者共同构成幂等键（见 2.2.3）。
2. **溯源强制**：凡是产出「结论」的契约（`BlackboardEntry`、`AgentResult`）必须携带 `sources[]`，标注来源类型与引用位置。这是《产品需求》「每个结论可回溯到来源数据、调用工具、模型版本与责任 Agent」的技术落点，不允许为空。
3. **预算传递**：`TaskEvent.budget` 在 `SubtaskDAG` → `AgentInvocation` 链路上逐级传递并单调收紧，任何 Agent 不得放宽上游给定的 `max_tokens` / `deadline`。

**版本策略**：`schema_version` 采用语义化版本。字段新增（可选）走小版本；字段语义变更或删除走大版本，并需同步迁移既有评测集。
